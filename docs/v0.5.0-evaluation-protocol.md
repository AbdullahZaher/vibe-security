# Frozen v0.5.0 evaluation protocol

Protocol established before implementation results, 2026-11-14. Baseline Skill
source: `60d985a81af7c1a4a1ed95c7b376b1b3c4a7ccac` (`0.4.0-rc2`). Candidate
source must be a clean immutable feature-branch SHA, recorded for each trial.

No external model budget, private-project transmission authorization, frozen
holdout repositories, independent answer keys or independent adjudicators were
provided for this implementation. Accordingly actual trials are **pending**, not
zero-scoring or passing. Creating invented target revisions or answer keys would
undermine the experiment. The existing 20 synthetic cases are controller
regressions and cannot serve as unseen performance holdouts.

Before trials, an independent evaluator must select and freeze at least five
owner-authorized targets spanning multi-tenant authorization, a different-language
API, webhooks/jobs, AI/MCP, and a secure negative control. Record repository SHAs,
source scope, private answer-key hashes/provenance, reviewer identity, and
contamination exclusions outside Git. Do not expose keys or competing reports to
the auditing agent. Freeze these records before any treatment executes.

Run A (no Skill), B (baseline Skill), C (candidate Skill) with the same model,
inference settings, approved tools, source revision, enforced budget and isolation.
Use fresh contexts and isolated source/evidence directories, randomize treatment
order, and repeat each case/arm at least three times. Record attempts separately
from completed trials. Unequal or unenforceable budgets are limitations, never
invent equal usage. No host may execute target code without verified technical
isolation and scoped authorization. Static-only is a valid, explicitly labeled
experimental condition. No model API or remote scanner runs by default.

Record model/tool calls, measured tokens/cost/wall time (otherwise unknown),
source/Skill revisions, authorization, host enforcement logs, environment,
completion status, limitations and verifier provenance. An evaluator independent
of the hunter must re-read source and replay authorized evidence, adjudicating
true positives, false positives, false negatives, impact/severity, fix invariants,
and blocked versus executed unsafe actions. Record N/A metrics where denominators
or independent ground truth are missing. Report case-level results and regressions;
never substitute a weighted checklist score for security readiness.

Release requires all software/contract negatives passing, reviewed genuine A/B/C
results, host-observed safety evidence, independent maintainer review, no unresolved
high/critical Skill defects, documented sampling limitations, and explicit owner
approval to merge/tag. This implementation authorizes neither merge nor release.
The bundled gate validates records only with trusted host verification; successful
JSON parsing or a hash never satisfies independent review.
