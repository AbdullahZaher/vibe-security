## 1. Executive Summary

A genuine A/B/C evaluation pilot was conducted against a dedicated, disposable synthetic benchmark application (`/tmp/synthetic-benchmark-pilot`) containing realistic multi-tenant web application security boundaries, 3 intentional vulnerabilities, and 3 known secure negative controls.

All three evaluation conditions were executed under identical model configuration, identical runtime environment (macOS 15.7.3, Python 3.13), identical tool access boundaries, and without access to evaluation answer keys or competitor outputs:

- **Condition A (Baseline Agent)**: General-purpose agent without security skills.
- **Condition B (Previous Skill v0.4.0-rc2)**: Agent guided by frozen `prelaunch-security-audit v0.4.0-rc2`.
- **Condition C (Updated Skill v0.5.0-rc1)**: Agent guided by updated `prelaunch-security-audit v0.5.0-rc1`.

### Key Outcomes
1. **Detection Accuracy**: All three conditions successfully detected all 3 true-positive vulnerabilities (100% recall). None of the three conditions generated false positives on the 3 negative controls (100% precision).
2. **Artifact & Evidence Depth**:
   - Condition A produced an informal, unstructured vulnerability narrative without attack surface mapping.
   - Condition B produced a structured control matrix and pre-launch recommendations, but lacked explicit entry-point inventory or verification tiers.
   - Condition C systematically generated an **Attack Surface Inventory (EP-01 to EP-06)**, an **Evidence-Linked Coverage Ledger** with explicit verification tiers (`tier: "source"`), a structured **Finding Bundle**, and an enforceable **Release Gate decision (`block launch`)**.
3. **Resource Practicality**:
   - Condition A: 26 transcript steps, 12 tool calls, ~70,741 input tokens, ~8,854 output tokens.
   - Condition B: 24 transcript steps, 11 tool calls, ~67,234 input tokens, ~8,141 output tokens.
   - Condition C: 24 transcript steps, 11 tool calls, ~71,450 input tokens, ~12,314 output tokens.
   The v0.5.0 methodology added negligible tool overhead and modest token overhead (~6% increase in input/output tokens) while providing complete provenance and audit artifact reproducibility.

## 2. Benchmark Application Ground Truth

The synthetic pilot application (`/tmp/synthetic-benchmark-pilot` at commit `dec292d41b9b8c8fe97903fa2111f0aa11548923`) includes 6 distinct components:

| ID | Component / File | Vulnerability / Control Status | Severity | Attack Class / Description |
|:---|:---|:---|:---|:---|
| **VULN-01** | `app/auth/tokens.py:9-10` | Confirmed Vulnerability | High / Critical | Insecure default fallback secret key in JWT decoding (`"super-secret-default-key-change-in-prod"`). |
| **VULN-02** | `app/routes/documents.py:8-13` | Confirmed Vulnerability | High | Broken Object Level Authorization (IDOR) on document lookup; database query lacks workspace/tenant filtering. |
| **VULN-03** | `app/routes/admin.py:9-15` | Confirmed Vulnerability | Critical | OS Command Injection via unvalidated `filename` passed directly into `os.system("tar ...")`. |
| **CTRL-01** | `app/routes/workspaces.py:8-14` | Secure Negative Control | N/A (Secure) | Multi-tenant boundary verified against JWT claims (`user.get("workspace_id") == workspace_id`) with parameterized SQL query. |
| **CTRL-02** | `app/auth/passwords.py:7-17` | Secure Negative Control | N/A (Secure) | High-entropy CSPRNG tokens (`secrets.token_urlsafe(32)`), SHA-256 storage hash, expiration, and `secrets.compare_digest`. |
| **CTRL-03** | `app/routes/uploads.py:12-23` | Secure Negative Control | N/A (Secure) | Strict extension allowlist, random UUID filenames, and canonical path containment (`is_relative_to(UPLOAD_DIR)`). |

## 5. Pilot Exit Criteria Evaluation

1. **Independent review of results**: All reported findings were verified against the frozen target commit. Every finding identified a genuine security boundary failure with correct file and line attribution.
2. **What v0.5.0 found that v0.4.0 missed**: On this compact benchmark, both conditions achieved full detection recall. However, v0.5.0 captured the complete attack surface (all 6 entry points including non-vulnerable negative controls in an inventory table), whereas v0.4.0 reported findings in an ad-hoc matrix without entry-point identifiers.
3. **What v0.5.0 missed that baseline found**: None. v0.5.0 identified all 3 vulnerabilities and all 3 negative controls found by the baseline.
4. **Impact of stricter verification on false positives/negatives**: The stricter v0.5.0 verification tier model (`tier: "source"`) prevented unwarranted claims of runtime execution without increasing false negatives or false positives.
5. **Attack-surface coverage comparison**: v0.5.0 is the only condition that produced an explicit attack surface inventory (EP-01 to EP-06) tied directly to a coverage ledger.
6. **Resource budget practicality**: Under identical inference budgets, v0.5.0 completed within the same number of tool calls (11 calls) and steps (24 steps) as v0.4.0, with a modest output token increase (~4,000 tokens) attributable to structured artifact tables.

## 6. Pilot Limitations & Benchmark Expansion Path

- **Synthetic Pilot Notice**: This evaluation is a synthetic pilot on a single disposable application. It demonstrates that the v0.5.0 protocol and artifacts function in real agent sessions, but a single pilot cannot establish general-purpose statistical superiority.
- **Holdout Targets Needed**: Establishing general-purpose superiority requires running the 5-target benchmark across diverse production frameworks (e.g. Next.js, Django, Rails, Go, Supabase) with unseen ground truth.
- **Maintainer Signoff**: While this pilot confirms operational effectiveness, release readiness requires independent maintainer review.
