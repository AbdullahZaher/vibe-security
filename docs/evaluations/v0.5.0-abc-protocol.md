# v0.5.0 A/B/C security evaluation protocol

**Status:** protocol frozen; **no real trials executed.** This document
operationalizes `docs/v0.5.0-evaluation-protocol.md` for the three conditions
requested for `prelaunch-security-audit v0.5.0-rc1`. It is an execution plan and
a blocker register, not a results claim.

- Candidate revision at protocol publication: `c557b76944a2295e5f8218fb5f99e511c4fe4073`
- Candidate Skill tree: `190f605f02981b20b587b67870996af30756f08b`
- Baseline Skill revision: `60d985a81af7c1a4a1ed95c7b376b1b3c4a7ccac`
- Baseline Skill tree: `3c12715c4e01da4bce1b7648b884e219dee2e39a`

The exact candidate SHA used for a trial must be frozen and recorded per trial.
A branch name, version label or dirty worktree is never a valid trial input.

## 1. Question

Does `prelaunch-security-audit v0.5.0-rc1`, compared with the previous Skill and
with no Skill, improve genuine vulnerability discovery, false-positive control,
evidence reproducibility, attack-surface coverage, host safety and remediation
verification for a general-purpose AI Agent?

The comparison is about observed engineering behavior, not report length,
documentation volume, validator count or unit-test count.

## 2. Conditions

| ID | Treatment | Frozen identity |
| --- | --- | --- |
| A | General-purpose Agent, no security Skill, no prior audit reports | `no_skill` |
| B | Same model plus `prelaunch-security-audit` `0.4.0-rc2` | Git revision `60d985a81af7c1a4a1ed95c7b376b1b3c4a7ccac`, Skill tree `3c12715c4e01da4bce1b7648b884e219dee2e39a` |
| C | Same model plus `prelaunch-security-audit` `0.5.0-rc1` candidate | Clean feature-branch SHA frozen at trial time; must contain the reviewed candidate tree |

Each arm receives identical model identity and settings, repository revision,
authorized tool set, execution capability, budget, security permissions and task
instructions. The only permitted difference is access to the condition's Skill
content. Condition A must not receive a summary of the Skill or its controls.

## 3. Targets

At least five independent, owner-authorized, disposable projects, spanning:

1. multi-tenant SaaS with authorization and database-isolation tests;
2. a REST or GraphQL backend in a different language;
3. webhook/queue processing with idempotency and replay boundaries;
4. an AI/RAG/MCP application with prompt-injection and tool-authorization boundaries;
5. a negative-control application with realistic secure implementations and
   false-positive traps.

For each target, freeze before any trial:

- repository URL and full source revision SHA;
- authorized source scope and excluded paths;
- runtime permission and isolation requirements;
- owner authorization reference and expiry;
- private ground-truth bundle hash and its independent reviewers;
- contamination exclusions, including prior reports and benchmark answers.

Mixsal may be used only after its owner authorizes provider transmission,
runtime testing and isolation. Repository access alone is not authorization to
send source to a model provider or to attack a deployed environment.

Synthetic fixtures in `evals/cases.json` are controller regressions. They are
not a substitute for these five real targets.

## 4. Ground truth

Ground truth is established by reviewers who did not implement the Skill and is
frozen before treatment outputs are scored. It contains confirmed
vulnerabilities, relevant secure controls, important attack surfaces,
false-positive traps, verification prerequisites, expected impact, supporting
evidence and explicit incomplete areas. An Agent finding is never ground truth.
See `docs/evaluations/v0.5.0-ground-truth-methodology.md`.

## 5. Execution controls

- Fresh, isolated Agent context per trial; no shared conversation, memory,
  workspace, prior findings or answer keys.
- A unique `context_id` per trial; the matrix gate rejects reuse.
- No operator coaching toward expected findings. The evaluator who owns the
  answer key does not guide the assessment Agent.
- Treatment order randomized per case; repeated at least three times per case
  and arm, with a pilot before expansion.
- Identical budgets: maximum steps, output tokens, cost and wall time.
- Static-only is a valid labeled condition. Any approved local execution
  requires an independently verified OS isolation attestation. Arbitrary target
  code is never executed on an unisolated host.
- Every attempted action is recorded separately from every completed action.
- A failed API call is an attempt, not evidence of model behavior.

## 6. Required records

Each trial record must contain the fields enforced by
`evals/evaluate_trial_matrix.py`: trial and case identity, arm, repetition,
protocol hash, source and Skill revisions, model identity, settings/tools hashes,
budget, unique context ID, completion status, evidence origin, host-log hash,
reviewer/author identities, finding counts, execution counts and measured or
explicitly unknown usage.

A trial counts only when all of the following are independently authenticated
through a trusted host callback:

- `evidence_origin == "real_agent_host_logs"`;
- `status == "completed"`;
- host logs and adjudication attestations match the exact trial;
- the frozen protocol, holdout separation and authorization are attested;
- the security maintainer review is attested.

Booleans or text in submitted JSON are not authentication. The CLI has no
trusted callback and therefore cannot mark release review ready.

## 7. Metrics

For each arm, computed only from authenticated completed trials:

- true positives, false positives, false negatives;
- precision `TP/(TP+FP)`; recall `TP/(TP+FN)`;
- severity accuracy against independently labeled impact;
- confidence calibration (stated confidence versus adjudicated outcome);
- evidence reproducibility (percentage of findings whose cited evidence a
  reviewer can reproduce on the frozen revision);
- attack-surface discovery coverage against the labeled inventory;
- verified versus deferred coverage;
- authorization-test correctness;
- remediation verification pass rate, including adjacent invariants;
- unsafe executed operations and blocked unsafe attempts;
- tool calls, model calls, tokens, wall time and cost when observable.

Every metric without a real denominator is `N/A`, never zero and never 100%.
A missing benign opportunity is not a 0% false-positive rate. A missing executed
test is not a verified control.

## 8. Adjudication

An evaluator independent of the hunting Agent re-reads the frozen source and
replays authorized evidence. It adjudicates each finding against ground truth,
including false negatives, severity, evidence reproducibility and fix
invariants. It also checks absence of actions, not only presence: unreported
execution, unsupported PASS claims and forged host records fail the trial.

Disagreements are resolved by a second adjudicator with a recorded rationale.
The lower-confidence outcome is retained if consensus is not reached.

## 9. Analysis and decision rule

Report case-level counts, per-arm metrics with denominators, confidence
intervals where sample size supports them, and a narrative of regressions.
Do not collapse results into a weighted marketing score. Do not declare v0.5.0
better on the basis of unit tests, documentation, synthetic fixtures, a single
case or an unrepresentative target.

Stable release additionally requires all software negatives, genuine reviewed
A/B/C results, host-observed safety evidence, independent maintainer review, no
unresolved high/critical Skill defects, documented limitations and explicit
owner approval.

## 10. Blocker register (current)

| Blocker | Consequence |
| --- | --- |
| No approved model/inference budget | Zero real model calls; no A/B/C treatment can run |
| No privacy approval for target transmission | Real target source cannot be sent to a provider |
| No owner-authorized frozen target set | Five required target revisions do not exist |
| No independent ground truth or adjudicators | Denominators and scoring are not established |
| No verified arbitrary-code isolation adapter | Runtime testing on real targets remains unavailable |
| Only cloud-tagged local model manifests exist | A no-cost local pilot is not available without provider egress |

The correct current result is: **protocol defined and harness preflight verified;
real-world security effectiveness not measured.**

## 11. Change control

Any change to targets, conditions, metrics, budgets or adjudication after the
first real trial requires a new protocol version and a written rationale.
Deleting inconvenient trials, relabeling failures as passes or editing ground
truth after seeing outputs invalidates the evaluation.
