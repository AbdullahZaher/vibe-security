# v0.5.0 ground-truth methodology

**Status:** method defined; **no ground truth has been established** because no
authorized target set or independent reviewer panel exists yet. This document
describes how ground truth must be produced before any A/B/C result is scored.
It does not contain invented vulnerabilities, severity labels or answer keys.

## 1. Independence

Ground truth is produced by reviewers who:

- did not implement, prompt-author or tune `prelaunch-security-audit`;
- do not adjudicate their own target code or their own found issues;
- do not guide assessment Agents toward expected answers;
- do not see treatment outputs before the label set is frozen;
- have read access to the frozen target source and written authorization to
  assess it.

At least two reviewers independently label each target. A third reviewer resolves
disagreements. Reviewer identity, context separation, timestamp and evidence are
recorded outside the public repository. Model output is never a label source.

## 2. Target freeze

Before labeling, record for each target:

- repository identity and full commit SHA;
- files, services and configuration in scope;
- excluded paths and deployed environments;
- language, framework, data stores and trust boundaries;
- owner authorization reference and restrictions;
- prior-report and contamination exclusions;
- runtime/isolation prerequisites.

The target source revision is immutable. A label set for one revision cannot be
reused for another revision without explicit revalidation.

## 3. Label construction

For each target, reviewers produce a private bundle with:

### Confirmed vulnerabilities

- stable vulnerability ID;
- title, affected component and exact source location;
- attacker prerequisites and required access;
- violated security invariant and trust boundary;
- safe reproduction on the frozen revision;
- expected impact and severity rationale;
- evidence references and verification prerequisites;
- known limitations or uncertainty.

A candidate is confirmed only when the independent reviewer reproduces the
issue or validates a deterministic proof from frozen source. A scanner alert, a
model assertion or a plausible pattern is not confirmation.

### Relevant secure controls

Controls that a correct audit should recognize as implemented, including the
evidence that would verify them. These are used to detect false alarms and
unsupported "not verified" claims.

### Important attack surfaces

Entry points, actors, resources, boundaries and data flows that a complete
assessment should enumerate. The list is explicitly non-exhaustive; unknown
outside-inventory assets remain unknown.

### False-positive traps

Realistic secure patterns that resemble common vulnerabilities, such as an
authorization check enforced in a shared middleware, parameterized queries with
safe dynamic identifiers, or a deliberately disabled debug route. Each trap
records why it is secure and what evidence proves it.

### Verification prerequisites

What a finding must demonstrate to be considered reproducible: test definition,
environment, disposable identity, expected failure/pass, revision and retained
host log. Conditional impact does not support confirmed high severity.

### Incomplete areas

Explicit unknowns. Missing ground truth is recorded as unknown, not silently
treated as "no vulnerability" or as a false-negative denominator.

## 4. Severity and impact

Severity is assigned from demonstrated impact on the frozen revision, not from a
scanner label. Use a documented scheme (for example CVSS with an explicit vector
and rationale) and record the assumptions. If impact depends on unavailable
runtime conditions, mark it conditional and do not use it to claim confirmed
high/critical severity.

## 5. Freeze and sealing

Before treatment outputs are inspected:

- export the label bundle to a private location outside the repository;
- compute a SHA-256 over the canonical bundle;
- record the hash, reviewer identities and freeze timestamp in the evaluation
  record;
- encrypt the bundle at rest (`evals/seal_evidence.py` or an equivalent
  authenticated-encryption workflow);
- restrict decryption to adjudicators.

No answer key, prior audit report, vulnerability list or labeled fixture is
placed in an assessment Agent's workspace, prompt, tool output or retrieval
index.

## 6. Scoring

Each Agent finding is matched to a ground-truth vulnerability by stable ID and
source location. Reviewers decide whether it is:

- a true positive with correct root cause and impact;
- a true positive with overstated severity/impact;
- a duplicate of another finding;
- a false positive against a secure control or trap;
- unverifiable and therefore not counted as a confirmed detection.

A ground-truth vulnerability with no matching Agent finding is a false negative,
provided the Agent's authorized scope included it. Findings outside the frozen
scope are recorded separately and are not silently counted as false positives.

Evidence reproducibility is scored by replaying the cited method on the frozen
revision in an authorized environment. A report claim is not replay evidence.
Remediation verification requires a baseline failure, a minimal patch, a
post-fix pass and adjacent invariant checks on the fixed revision.

## 7. Handling disagreements

- Record both reviewers' labels and rationales.
- Resolve by source re-read and, where authorized, safe reproduction.
- Retain a dissenting label in the private record.
- If consensus is impossible, exclude the item from the primary denominator and
  report it separately as disputed. Do not choose the label that makes a
  treatment look better.

## 8. Anti-contamination controls

- Fresh Agent context per trial; no shared memory or workspace.
- No ground-truth or competitor output in the Agent's repository, tools or
  retrieval corpus.
- No evaluator hints, leading questions or iterative answer correction.
- Randomize treatment order.
- Record any accidental disclosure and invalidate affected trials.
- Do not reuse synthetic fixture labels as real-target ground truth.

## 9. Limitations to publish

- Ground truth can be incomplete; absence of a label is not proof of security.
- Reviewers may share blind spots or be influenced by the same patterns.
- Model training data may contain public target code or prior reports; this
  cannot be fully excluded and must be disclosed.
- Severity is judgment-based even with a scoring scheme.
- A small target sample cannot establish general-purpose performance.
