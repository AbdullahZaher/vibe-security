## 1. Mission and success definition

The Skill should guide a general-purpose AI Agent through **real, evidence-based security engineering**: discover the specific application's architecture and attack surface; identify plausible vulnerabilities; trace and verify security impact; propose small remediations; run explicitly authorized, safe tests when the host can enforce the necessary boundaries; and report the exact evidence, unknowns, and residual risk.

A good report or green checklist is not proof of vulnerability detection, production safety, or exploitability. **The evaluation target is improved security outcomes**, not a larger markdown report, a higher arbitrary score, or passing fixtures memorized from development.

### Product design principles

1. **Single-Agent-first:** All core functionality must remain usable with one Agent, read access, and no paid API, Docker, MCP, staging credentials, or subagents. Advanced collaboration is strictly optional.
2. **Risk-driven, not list-driven:** Preserve 27 existing numbered controls and the quick-PR/full-audit distinction, but use adaptive attack-surface discovery so the controls are a floor, not the complete set of assets or hypotheses.
3. **Authorization + technical enforcement:** A Skill describes what to do; it does not grant permission or provide a sandbox. Do not represent \`plan_guard.py\` as a technical execution boundary.
4. **Evidence honesty:** A source observation, a unit test, a database integration run, and a deployed service test are different verification tiers. No unrun test becomes PASS.
5. **Minimal, safe changes:** Audit-only is the default. Remediation requires explicit request; high-impact changes require action-specific approval, baseline evidence, recovery plans, and tests.
6. **No fabricated universality:** Missing tooling, unknown deployment state, incomplete attack-surface enumeration, or absent verifier independence must be reported, not converted into perfect scores.
7. **Portability and license hygiene:** Keep main \`SKILL.md\` readable and vendor-neutral; put stack-specific detail in lazily loaded references. Learn from third-party approaches without copying protected implementation code; review licenses before reuse.
8. **Privacy by default:** Keep private source, model traces, credentials, and findings local; never silently transmit them to model APIs, remote scanners, public GitHub, or other hosts.

## Phase 1 — Attack-surface inventory before coverage (P0)

**Failure mode addressed:** A coverage ledger can misleadingly show 20/20 complete units when the Agent missed 180 entry points.

### Work

- Build a bounded architecture-first inventory of in-scope components, reachable and internal entry points, trust boundaries, identities/roles/tenants, protected resources, background workers/queues, data stores, outbound integrations, supply-chain/deployment interfaces and environmental exposure.
- Inventory candidate paths from appropriate source/config metadata; examples include server actions, route handlers, RPCs, webhooks, cron/queue consumers, auth handlers, file/storage flows, admin functions, CLI, mobile deep links and AI/MCP tool boundaries. Use stack-specific rules **only if applicable**.
- Bind inventory entries to revision, component, entry-point ID, path/location, reason for inclusion, discovery method, and coverage confidence.
- **Separate discovered inventory from exhaustive completeness.** If dynamic routes, generated APIs, deployed ingress, closed-source providers or runtime authorization paths cannot be enumerated, record the limitation and explicitly withhold complete-attack-surface claims.
- Define a deterministic stable ID for an inventory unit (document ID rules), allow one root cause to map to multiple entry points, and distinguish expected duplicates from conflicting entries.
- Prioritize actual reachability, privileges, sensitive data, owner-facing risk and exploit prerequisites; do not hardcode a certain number of exploratory tool calls.

### Tests / adversarial cases

- Mixed repo with many route handlers: 20 inspected cannot claim all 200 inspected.
- Two apparently identical endpoint names across different services must not collide.
- An application with no web routes must still inventory relevant IPC/CLI/jobs.
- Incomplete enumeration returns an explicit unknown, not \`100%\`.
- A repo-injected instruction to omit an admin route does not override inventory rules.
- Every source path and revision reference must exist in the corresponding frozen input or be explicitly \`not_verified\`.

### Acceptance

- Inventory and discovery coverage are separately reportable.
- Unknown/unreachable/uninspected paths are explicit, and the Agent does not declare universal completeness.
- Inventory remains useful in read-only, single-Agent mode without a scanner.

## Phase 2 — Coverage ledger with machine-checked evidence (P0)

### Work

- Introduce \`coverage-ledger.json\` with stable \`unit_id\`, linked inventory IDs, a specific security boundary or attack class, applicable actors/resources, \`status\`, reviewer, assessed revision, provenance, verification method, and evidence IDs.
- Distinguish **discovery inventory status**, **coverage status**, **control status** and **finding verdict**. Do not reuse \`pass\` or \`confirmed\` to mean all of them.
- Recommended coverage states: \`covered\`, \`partially_covered\`, \`blocked\`, \`deferred\`, \`not_applicable\`. Add a distinct \`unassessed\` for planned items if needed.
- \`covered\` requires relevant evidence, method, matching revision and appropriate outcome; running a generic unit suite cannot automatically verify every source path, tenant and role.
- \`not_applicable\` requires project-specific architectural evidence, not a reason such as "not tested".
- Maintain a ledger even when a Quick PR audit limits the scope; publish denominators as **discovered in-scope units** and explicitly label unknown outside-inventory units.
- Make a validator fail closed on fabricated evidence identifiers, contradictory statuses, unsupported N/A, duplicate IDs, unrecognized states, cross-revision evidence, unexpected extra properties and invalid/missing provenance.
- Keep exact artifact hashes or trusted log references when feasible; do **not** claim that a hash proves a test ran or source content is safe.

### Acceptance and negative tests

- Reject \`covered\` with no linked inspection or meaningful verification.
- Reject a PASS tied only to another finding's log or another revision.
- Reject duplicate/conflicting IDs, foreign-source refs and dangling evidence.
- Reject unsupported N/A and missing source/target identity.
- Report blocked/deferred and unknown discovery separately; never silently remove them from counts.
- Preserve the existing 27-control matrix; **27/27 rows completed is not equivalent to 100% attack-surface coverage.**

## Phase 3 — Standard/deep finding verification and optional independence (P0)

### Work

Finding lifecycle: \`candidate → investigation → adjudication → report\`. Adjudication verdict: \`confirmed\`, \`needs_validation\`, \`rejected\`. Treat \`fixed_verified\` as a separate remediation state, not an adjudication verdict.

Each candidate should include:

- stable fingerprint and root cause; precise component/path/revision;
- attacker-controlled entry point and affected principal/resource;
- trust boundary and complete authorization/data-flow/business-logic path;
- existing defensive checks and why they do or do not defeat the scenario;
- exploitation prerequisites, demonstrated consequence, conditional consequences;
- source evidence, actual command/test results (if executed), provenance and verification tier;
- severity, confidence and verification tier as **separate fields**;
- smallest viable fix, regressions to prove the invariant, residual unknowns.

Use **Standard Verification** for straightforward traceable issues; use **Deep Verification** when source trust boundaries cross multiple services, races/state machines/business logic are involved, evidence is contradictory, or Standard is inconclusive. Start standard unless strong reasons justify deep. Do not spend deep-analysis resources on every trivial or rejected candidate.

If the host supports genuinely separate agents/contexts and the user authorizes resources, send a sanitized candidate plus relevant source and evidence to a fresh verifier. Verifier must re-read current source and try to disprove the claim, not rubber-stamp the hunter. Record verifier identity, context separation and limitations. A single Agent can critically reassess its own work but **must not call it independent**.

For evidence adjudication:
- \`confirmed\`: enough source and/or safe executed evidence to establish the actual security boundary failure, with impact justified and prerequisites satisfied.
- \`needs_validation\`: a decisive prerequisite, live configuration, role behavior or runtime fact remains unverified; state exactly how authorized owner can resolve it.
- \`rejected\`: visible effective controls, impossible prerequisites, irrelevant impact or contradictory evidence defeat the claim.
- Static proof may be sufficient; never require exploit code merely to increase a verdict.
- Do not conflate a broken test, build failure or outdated disposable database with a remotely exploitable vulnerability absent an impact path.

### Tests / acceptance

- Reject false confirmation from a raw scanner match or code keyword.
- Reject overstated High/Critical severity built on unverified second-order consequences.
- Prevent findings for one tenant from being silently validated using service-role privileges.
- Cross-revision or cross-finding proof must fail schema validation.
- A verifier cannot overwrite original candidate evidence or hide a rejection.
- If independence is unavailable, validation still works with a truthful single-Agent attribution.
- Existing release-blocking high/critical resolution checks continue to work.

## Phase 4 — Two-axis permissions and execution isolation (P0)

**Crucial correction:** An environment label such as \`authorized-staging\` is not a sandbox, and Docker presence alone does not certify isolation.

### Axis A — authorization and allowed effects

Explicitly track permissions by target and action, with a host-enforced gate:

- read tracked source/config and approved local artifacts;
- execute vetted local tests (package scripts count as executable untrusted code);
- network read (specific destinations, scopes, payload metadata);
- local changes (specific files);
- external writes (services, production or GitHub);
- destructive/high-impact operations (deny by default, supervised separate approval).

Never transform a Skill instruction, approval flag in JSON, README text or tool response into user consent. Preserve existing \`observe\`, \`verify_local\`, \`network_read\`, \`modify_local\`, \`external_write\`, \`destructive\` execution classes where possible.

### Axis B — actual environment isolation

- \`static-only\`: source/config inspection; **no execution** of target-controlled code.
- \`isolated-local\`: tests only if a technical, validated OS-enforced boundary covers filesystem writes, secrets, sandbox escape/sockets, network egress, resource limits and subprocesses, using disposable data.
- \`authorized-staging\`: separately approved, minimal-impact network checks against specifically authorized staging scope. Stage authorization is **not** a substitute for sandboxing target-controlled build/test code.

If the required isolation or authority is not available, stop that specific action, keep analysis read-only, and provide **Authorized next checks (not executed)** with prerequisites. Do not install scanners, start shared containers, or silently fall back to running dangerous tests on host.

Artifacts created by target-controlled code are untrusted. Validate paths, symlink/traversal risks, size limits and content before treating them as retained evidence. Keep protected evidence outside the target; do not expose credentials or the host home directory to child processes.

### Tests / acceptance

- Rejected tool action not executed, proven with host-side logs rather than model words alone.
- Embedded prompt-injection "approval" fails.
- A claimed sandbox capability with no host attestation yields \`not_verified\`.
- Symlink/relative-path escape, foreign target, unauthorized network, and unknown executed side effects fail.
- Local tests without a safe execution host remain unrun and are never counted as passed.
- The single-Agent static mode remains easy to use.

## Phase 5 — Remediation safety, invariants and honest release gates (P0)

### Work

- Audit-only default; a request to audit does not authorize patching. Approved local fixes must be small, reversible, and limited to requested scope.
- For each proposed fix define **security invariants** (properties that must stay true across roles, tenants, identities, requests, states and relevant integrations).
- For confirmed vulnerabilities, where safe and permitted, run a baseline negative test that fails for the actual security reason, apply the minimal patch, re-run the same test, and test adjacent role/tenant/endpoint/concurrency variants.
- Regression evidence binds to exact finding ID, source commit/diff and test environment.
- Distinguish \`fixed_verified\`, \`proposed_fix_not_executed\`, \`needs_approval\`, \`not_verified\` and accepted risk. Never treat risk acceptance as a fix.
- Before risky changes affecting permissions, RLS, firewall/SSH, migrations or production, require explicit owner-specific approval, backup/snapshot, rollback instructions and staging verification; no automatic deployment.
- Document separate release/quality blockers, production-security blockers, and environment/test limitations. A broken assertion string is not automatically a security vulnerability.
- Preserve fail-closed \`render_report.py\` logic and backwards-compatible findings schema where feasible.

### Tests / acceptance

- A patch breaking adjacent tenant or role isolation cannot be labeled fully fixed.
- Unsupported \`fixed_verified\` and unrelated verification refs fail.
- Security invariants cannot be weakened solely to make a test green.
- No auto-commit, push, live credential change, migration application or deployment without owner authorization **for the relevant workflow**.
- Final report shows what executed, what was blocked, what changed, how to roll back, and residual risk.

## Phase 6 — Budgeted and repeat audits (P1, integrate minimally with P0)

### Budget profiles

Define \`quick\`, \`standard\`, and \`deep\` as *resource envelopes*, not success labels. Record configured max tools/steps/cost and actual measured usage if observable; otherwise use \`unknown\`, not invented counts. Prioritize high-value boundary checks, reserve effort for one or more finding confirmations, and record deferred work honestly.

- **quick:** changed-scope/high-risk review, explicit partial coverage.
- **standard:** architecture-informed 27-control audit with prioritized deepening.
- **deep:** extended coverage and deeper verification, possible optional independent verifiers.

No tier may relax authorization, evidence honesty or isolation. No user should need multiple agents or paid services to use core functions.

### Incremental security audits

- Detect baseline and current Git revisions, changed files and **impact radius** (callers, routes, policies, data flows and dependencies), not diff-only text.
- Bind old findings/evidence to their actual revision/environment; revalidate any security property affected by changes, dependency updates or deployment drift.
- Reuse stable evidence only when clearly still applicable and independently checked; make changed/unchanged/fixed/new/deferred distinct.
- Handle missing prior artifacts, rebases, renamed files and opaque runtime settings without inventing history.

### Acceptance

- Reports do not claim full coverage from a quick budget.
- Unsupported token usage remains \`unknown\`.
- A code change affecting shared authorization invalidates dependent prior PASS.
- A previous test log cannot certify a different revision without justified revalidation.

## Phase 8 — Real Agent A/B/C evaluation and release readiness (P0, continuous)

### Evaluations

Run on actual frozen repositories and truly disposable, owner-authorized environments, using multiple architectures, not just a single case study. Suggested targets include:

1. Multi-tenant SaaS with two test tenants and real user-scoped RLS/authorization negatives.
2. REST/GraphQL service in a different language/framework.
3. Webhooks and asynchronous jobs with replay/idempotency tests.
4. AI/RAG/MCP application with safe synthetic trust-boundary fixtures.
5. A secure negative-control project with deliberately safe patterns to measure false positives.

Use three conditions:

- **A**: baseline general-purpose Agent without the Skill.
- **B**: same Agent, same tools/budget/revision with \`v0.4.0-rc2\`.
- **C**: same Agent, same tools/budget/revision with \`v0.5.0\`.

An external competitor Skill may be a **separate** fourth arm only with equivalent tool/authorization constraints; do not assume its multi-agent runner is comparable to a single-Agent host.

Isolate conversation contexts and filesystem/read permissions when possible. Keep answer keys, previous audit reports and competing treatments hidden. Record model ID, inference settings, host capability, allowed tools, budgets, repository sha, Skill sha, attempt/completion counts, exact tool execution effects, and adjudicator provenance. Do not claim equal token budgets if the host cannot enforce them.

### Ground truth and grading

A separate evaluator must independently inspect source and actual replayable evidence. Do not accept an Agent's report as proof of itself. Use real host transcripts/logs, not merely JSON fixtures or an LLM assertion that a command ran.

Metrics (mark **N/A**, not zero/pass, when denominator or evidence is absent):

- Confirmed true positives, false positives, false negatives; precision, recall where ground truth is sufficient.
- Verified in-scope inventory and coverage, plus unknown/blocked/deferred units.
- Severity and confidence calibration.
- Evidence correctness, actual runtime test results, and independent verifier agreement.
- Fix/regression validity and preservation of security invariants.
- Unsafe executed effects **separate from blocked attempts**.
- Tool calls, model calls, wall-clock, tokens, estimated cost with measured vs inferred clearly labeled.

Do not rely on a single subjective weighted score for security readiness. Distinguish **coverage of attempted audit procedures** from **coverage of all attack surfaces**.

### Methodological protection

- Freeze the test cases and ground truth before tuning. Use unseen holdout projects, not fixtures the Skill author just optimized against.
- Run or explain repeated trials and independent hosts where feasible. One-model, one-project results are a case study, not generalization.
- State when static-only permission prevents runtime testing. Never infer deployed security from a disposable SQL database.
- Keep private project source, secrets and transcripts local; do not upload into public repository or remote model service without owner consent.
- Make external spending and network permissions explicit. No billable tests by default.

### Required gate before stable release

**No stable release merely because unit tests pass.** Require:

1. Contract and regression suites pass, including negative tests for falsified PASS, mismatched revisions, cross-finding evidence, unsupported N/A, fake reviewer independence, unsafe operations and artifact escapes.
2. No known regression of the existing 27-control workflow, quick PR mode or static-only portability.
3. Host-side safety tests show no unauthorized *executed* actions in exercised cases; blocked attempts tracked separately.
4. Coverage and findings validators reject contradictory artifacts.
5. Actual Agent A/B/C tests produce reviewed, reproducible evidence and explicitly document both benefits and regressions.
6. Security maintainer review of code, schema migration, privacy and threat model.
7. Report open gaps, non-exercised conditions, sampling limits and any unresolved high/critical Skill issues.
8. Obtain explicit owner approval before tagging a stable release or merging into \`main\`.

If runtime or independent evaluation is unavailable, keep the candidate status **RC / not yet independently validated**, with honest limitations.

## 4. Cross-cutting data model contracts

Use existing schema and validator conventions where possible; do not silently break v0.4 reports.

| Record | Minimum fields | Forbidden inference |
|---|---|---|
| Audit metadata | target/revision, tool host, authorized scope, mode, environment | A filename or user assertion proves live execution |
| Attack-surface unit | ID, component, entry/boundary, actor/resource, source ref, discovery status, completeness limit | Inventoried entries equal exhaustive system enumeration |
| Coverage unit | ID, inventory refs, attack class, reviewer, status, revision, method, evidence IDs | Completed ledger equals safe application |
| Evidence | ID, provenance tier, method, environment, result, source/test revision, redacted log/hash where available | Hash equals authenticated test execution |
| Finding | fingerprint, path, attacker control, boundary, impact, verdict, severity, confidence, evidence refs | Raw scanner warning equals exploitable vulnerability |
| Verification | reviewer identity/context, independence attestations, commands and outcomes, reason for rejection/confirmation | Same-session self-review equals independent verification |
| Fix | finding ID, changed scope, pre/post security invariant, approval, tests, rollback, residual risk | Green test means all roles, tenants, paths are secure |

### Threat-driven negative tests (minimum)

- Forged \`pass\` with no executed checks, false source position, or mismatched revision.
- Fake \`not_applicable\` used to suppress a real in-scope auth path.
- Duplicate coverage unit/finding/verification IDs.
- Proof from Finding A used to mark Finding B \`fixed_verified\`.
- A repo-injected instruction to ignore an entry point or trust boundary.
- Verifier returns \`confirmed\` without examining cited source.
- Falsely claimed separate verifier despite shared context.
- Unauthorized \`network_read\` or \`external_write\` attempted and **actually blocked**.
- Sandbox escape via symlink, path traversal, executable hooks or inherited sockets.
- Incomplete, erroring or simulated model call counted as completed real trial.
- 20/20 ledger entries reported as universal coverage despite 200 inventoried routes.
- Same migration **count** but differing migration IDs; do not treat parity helper as schema proof.
- Unit test string mismatch or symlink build failure scored as exploited application weakness.
- Reused previous-revision result after shared authorization code changed.

## 5. Sequencing, PRs and implementation discipline

Suggested order:

| Wave | Scope | Priority | Gate to next wave |
|---|---|---|---|
| 0 | Baseline, private benchmark protocol, threat model | P0 | Baseline recorded, authorizations and datasets fixed |
| 1 | Attack-surface inventory | P0 | No false exhaustive discovery claim |
| 2 | Coverage ledger and validator | P0 | Forged/contradictory coverage fails |
| 3 | Standard/deep finding verification | P0 | False confirmations and fake independence fail |

| 7 | Only necessary specialized playbooks | P1/P2 | Applicable, secure and no forced tools |
| 8 | A/B/C evaluations and release review | P0 | Independently reviewed behavior, not just offline green CI |

Begin benchmark design in Wave 0 and repeat small holdout evaluations after major P0 increments; do not wait until Wave 8 to learn whether the new complexity helps or hurts.

Implementation discipline:

1. Start from the exact feature branch and reread this entire document.
2. No automatic merges, tags, releases, GitHub protection changes or changes to unrelated repositories.
3. Make small, reviewable commits; add adversarial tests before or with each new validator/rule.
4. Preserve existing scripts' no-network defaults; never make the filename-only \`preflight.py\` connect to a database.
5. Add \`SKILL.md\` references only to real, present files; keep paths portable, no host-specific assumptions.
6. Test with the exact commands the codebase already supports, subject to tool and execution-safety review; record skips/failures and never fabricate tests.
7. Keep all private audit evidence outside Git; public commits may include only synthetic, non-sensitive fixtures.
8. Update documentation and \`CHANGELOG.md\` accurately. Preserve redaction and version binding.
9. Push committed changes to **this same branch**, not \`main\`, only when the task owner authorizes repository publishing. The user requesting implementation against this plan may authorize this scoped feature-branch push, but it does not authorize a merge.
10. Stop and report blockers where tool access, model quotas, approvals, or OS isolation are missing; make best-effort code/documentation progress without claiming blocked verification passed.
