## 3. Mandatory Blocking Issues for Stable Release

The following gates are currently blocking stable release certification:

1. **Gate 10 — Independent Human Maintainer Authorization:**  
   In compliance with the project charter and governance rules, AI agents cannot approve or sign off on production releases. Only an authorized human repository maintainer can grant stable release publication.
2. **Gate 5 — Statistical Evaluation Matrix Completion:**  
   The protocol mandates 45 independent trials (5 cases × 3 arms × 3 repetitions). Developer logs claim one multi-project session per arm. They do not independently authenticate 15 separate case trials. The full 45-slot matrix remains unverified; do not subtract three unvalidated sessions from the required trial count.
3. **Gate 9 — Repository Branch Protection Enactment:**  
   The repository owner must verify that the GitHub repository branch protection rulesets on `main` and `feat/prelaunch-security-audit-v0.5.0-plan-20261114` enforce:
   - Require a pull request before merging (minimum 1 approved review from a human security maintainer).
   - Require status checks to pass before merging (`unit-and-contract`, `mcp-stdio-integration`).
   - Require signed commits.
   - Require linear history (no merge commits, rebase or squash only).
   - Do not allow bypass of the above settings.

## 4. Rollback and Recovery Plan — Corrected, Non-Destructive by Default

The commands below are **human-run examples only**, never automatically executed by the Skill or a CI workflow. First verify repository ownership, protected branch status, the exact merge strategy and a clean local checkout. An incident responder must approve the rollback, incident containment and preservation of evidence.

### Step 1 — Freeze and Contain

1. Suspend release publication and disable any host authorization issuer or integration suspected compromised; preserve audit logs, CI artifacts and immutable source identifiers.
2. Keep the static-only execution guard enforced; do not reactivate the old Seatbelt executor as part of recovery.
3. Identify the deployed/tagged commit and the exact PR merge strategy. Do not use force-push, `git reset --hard` or silently rewrite protected history.

### Step 2 — Safely revert an accepted change on a new authorized branch

**If the PR was merged as a true merge commit**, and the parent relationship was independently confirmed:

```bash
git switch -c revert/v050-incident
git revert -m 1 --no-edit <VERIFIED_MERGE_COMMIT_SHA>
# Run applicable tests; open a reviewed rollback PR, do not push directly to protected main.
```

**If it was squash-merged or fast-forwarded as a single ordinary commit**:

```bash
git switch -c revert/v050-incident
git revert --no-edit <VERIFIED_SQUASH_OR_ORDINARY_COMMIT_SHA>
# Run applicable tests; open a reviewed rollback PR.
```

Do not use `git revert -m 1` for a non-merge commit. `-m 1` means the **merge parent's index**, not a commit message. For multiple rebased commits, plan individual inversions in verified reverse dependency order. Rollback must retain any security guard that blocks untrusted execution unless a separately approved replacement is deployed.

### Step 3 — Revoke compromised approvals at the trusted issuer

**Do NOT delete `approvals.json` or `approvals.json.lock`.** These files contain replay-prevention state. Removing them can erase consumption history; it does not inherently revoke authorization tokens and can permit prior tokens to be accepted again by an issuer that still trusts them.

1. Stop acceptance of affected authorizations in the **trusted host/issuer**, not by deleting the consumption ledger.
2. Revoke, rotate, or invalidate affected tokens, credentials and authorization references at their authoritative source; use an epoch/version change or expiry where supported.
3. Preserve the durable consumed-token ledger and lock file with proper owner-only permissions as evidence; securely snapshot them under incident retention policy.
4. Refuse all affected requests until both authorization revocation and replay blocking are verified across independent processes.
5. If the issuer lacks revocation, fail closed at its policy boundary and record the inability as a release blocker.

### Step 4 — Independently confirm recovery

Re-run the targeted exploit reproducer, approval replay and corruption tests, source-only access tests, and all applicable host negative controls against the frozen rollback candidate. Independently verify the exact GitHub status checks, approval chain, final Git tree and live capability restrictions before a new release decision.

**Primary references:** [Git revert official documentation](https://git-scm.com/docs/git-revert), [NIST SP 800-63B replay resistance](https://pages.nist.gov/800-63-4/sp800-63b.html), [GitHub branch protection guidance](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
