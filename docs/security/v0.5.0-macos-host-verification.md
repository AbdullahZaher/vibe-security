## 1. Executive Summary

This report documents the independent host-level execution and negative testing of the runtime isolation and authorization controls in `prelaunch-security-audit v0.5.0`.

All 10 mandatory negative security tests were executed directly on authorized macOS hardware against disposable synthetic fixtures. **All 10 tests passed (10/10, 100% pass rate).**

### Key Security Invariants Confirmed:

1. **Untrusted Code Execution Is Disabled and Unreachable:**  
   The candidate Skill adapter (`IsolatedHostAdapter`) strictly fails closed for all untrusted subprocess execution requests. No dispatch pathway to `/usr/bin/sandbox-exec` or subprocess execution remains active. Mutating configuration flags (e.g. `RUNTIME_EXECUTION_ENABLED = True`) cannot bypass the block.
2. **Static-Only Capability Scope:**  
   The runtime broker provides only bounded, allowlisted read-only file access (`StaticHost`), using strict canonical path checks, component-wise `O_NOFOLLOW` with directory file descriptors (`dir_fd`), and size bounds (max 1,000,000 bytes).
3. **Atomic Single-Use Durable Approvals:**  
   `ApprovalStore` guarantees single-use authorization consumption across processes and instances using private host directory pinning (`0o700`), locked regular files (`0o600`), `fcntl.flock(LOCK_EX)`, unpredictable atomic file replacement with `O_EXCL`, and `fsync`. Replay attacks across instances fail closed.
4. **POSIX Boundary & macOS Seatbelt Limitations Proved:**  
   Test 6 empirically demonstrated that on macOS Darwin, child processes calling `setsid()` create an independent session that escapes `os.killpg()` process group signaling. Furthermore, Darwin Seatbelt (`sandbox-exec`) is deprecated by Apple and lacks cgroup-style memory, CPU, or PID quotas. These empirical findings substantiate why arbitrary untrusted code execution cannot be safely offered without external hypervisors (microVMs), and justify keeping execution disabled in v0.5.0.

## 4. In-Depth Analysis of Individual Negative Tests

### Test 1: Unauthorized Subprocess Execution
- **Mechanism:** `IsolatedHostAdapter` configured with an attestation provider that refuses authorization (`lambda _r: None`).
- **Input:** Request targeting `isolated-local` with effect `verify_local` and operation `run_test`.
- **Observation:** `dispatch()` evaluated the request through `assess()`, which detected missing host attestation and returned `status: 'not_verified'`, `reason: 'trusted host authorization unavailable'`. `dispatch()` immediately returned `occurred: False, blocked: True` without executing any subprocess.

### Test 2: Static-Only to Execution Escalation
- **Mechanism:** Request constructed with `effect: 'observe'` and `profile: 'static-only'` attempting to dispatch a command through `IsolatedHostAdapter`.
- **Observation:** `dispatch()` enforces strict effect/profile binding:
  ```python
  if request.get("effect") not in {"verify_local", "modify_local"} or request.get("profile") != "isolated-local":
      event["reason"] = "subprocess dispatch requires explicit isolated-local execution authorization"
      return {"occurred": False, "blocked": True, "reason": event["reason"]}
  ```
  The escalation attempt was rejected at line 493 of `runtime_host_adapter.py`.

### Test 3: Host Filesystem Scope Enforcement
- **Dual Layer Verification:**
  - **Layer 1 (StaticHost Broker):** An agent attempting path traversal via `../outside3/forbidden.txt` was rejected by component-wise path validation and `trusted_root()` checks, returning `DENIED by static host`.
  - **Layer 2 (OS Seatbelt):** A subprocess executed under `sandbox-exec` attempting to read `/outside3/forbidden.txt` failed with returncode `1` and stderr `cat: /outside3/forbidden.txt: Operation not permitted`.
  - Content check: The string `FORBIDDEN_CONTENT` was never leaked to stdout.

### Test 4: Credential and Home Directory Denial
- **Target:** Sensitive host files permitted by default macOS system profiles (`/etc/passwd`, `/private/etc/master.passwd`) and user home credentials (`~/.ssh`).
- **Observation:**
  - The Seatbelt profile explicitly incorporates:
    ```scheme
    (deny file-read* (literal "/private/etc/master.passwd"))
    (deny file-read* (literal "/etc/master.passwd"))
    (deny file-read* (literal "/private/etc/passwd"))
    (deny file-read* (literal "/etc/passwd"))
    ```
  - `cat /etc/passwd` exited with code `1` and `Operation not permitted`.
  - `ls ~/.ssh` exited with code `1` and `Operation not permitted`.

### Test 5: Unauthorized Network Egress Denial
- **Target:** Network socket connections to loopback or external hosts.
- **Baseline:** Direct `nc -z -G 1 127.0.0.1 <port>` succeeded with exit code `0`.
- **Sandboxed Attempt:** Under Seatbelt `(deny network*)`, `nc -v -z -G 1 127.0.0.1 <port>` exited with code `1` and stderr `nc: socket: Operation not permitted`.

### Test 6: Detached Descendant Process Persistence (`setsid`)
- **Vulnerability Scenario:** Untrusted target code creates a background daemon by calling `os.fork()`, followed by `os.setsid()`, and a second `os.fork()`.
- **Empirical Proof:** When the parent process was terminated via `os.killpg(proc.pid, signal.SIGKILL)`, the grandchild process in the new session created by `setsid()` survived.
- **Significance:** This empirical finding confirms that POSIX process groups cannot contain session-detached descendants on Darwin. This proves that user-space Seatbelt cannot guarantee process containment or cleanup, directly validating the design decision to **default-disable arbitrary untrusted code execution in v0.5.0**.

### Test 7: Approval Replay Across Processes
- **Mechanism:** `ApprovalStore` backed by `approvals.json` in a private directory mode `0o700`.
- **Execution:** Instance 1 consumed key `req-replay-1:auth-token-xyz:<spec-hash>` (returned `True`). Instance 2 (representing a concurrent or subsequent process) attempted to consume the same key and was rejected (returned `False`).
- **Durability:** File permissions were verified as regular file `0o600` and lockfile `0o600`. `store.clear()` raised `PermissionError` when attempted on durable storage.

### Test 8: Malformed or Forged Attestations
- **Mechanism:** Request submitted with host attestation containing a forged `command_sha256` digest (`0000...0000`).
- **Observation:** `assess()` verified `digest(cmd)` against `attestation.command_sha256`, detected the forgery, and returned `reason: "command does not match authorized command_sha256"`. Dispatch failed closed (`blocked: True, occurred: False`).

### Test 9: Command and Spec Substitution
- **Mechanism:** Request authorized for command `python3 -c "print('ORIGINAL')"`, but dispatched with substituted command `python3 -c "print('SUBSTITUTED')"`.
- **Observation:** `dispatch()` verified structural identity before evaluating policy:
  ```python
  if "command" not in request or request["command"] != command:
      event["reason"] = "command is not cryptographically or structurally bound to request"
      return {"occurred": False, "blocked": True, "reason": event["reason"]}
  ```
  The substitution attempt was rejected prior to any host action.

### Test 10: Runtime Configuration Manipulation
- **Mechanism:** Simulated runtime flag manipulation by mutating `runtime_host_adapter.RUNTIME_EXECUTION_ENABLED = True`.
- **Observation:** `dispatch()` evaluated the request, verified that no external supervisor exists, and returned:
  `"untrusted code execution disabled; external isolation supervisor not implemented"`
  No subprocess was spawned. Crucially, the approval store was untouched (`approvals.json` was not created or modified), proving that denied requests never consume approvals.

## 5. Architectural Boundaries and Limitations

1. **Host-Enforced vs. Skill-Enforced Boundaries:**
   - Darwin Seatbelt is an OS-level mechanism (`/usr/bin/sandbox-exec`), not a Skill sandbox. Apple has deprecated this interface without providing a direct user-space replacement.
   - The Skill cannot provide multi-tenant containment or resource quotas on macOS developer machines.
2. **Current Supported Scope:**
   - **Supported:** Static-only code review, AST inspection, Git diff analysis, and allowlisted file reads via `StaticHost`.
   - **Disabled:** Subprocess execution of target code, dynamic test execution, network calls, and arbitrary filesystem writes.
3. **Requirement for External Hypervisors:**
   - For multi-tenant or untrusted dynamic code execution, a dedicated external supervisor (e.g., Firecracker microVM, Kata Containers, or cloud sandbox) with independent hypervisor-enforced memory, disk, network, and process isolation must be provisioned and authorized.
